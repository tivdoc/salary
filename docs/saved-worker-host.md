# Saved worker host boundary

`src/server/product/processing/saved-worker-host.ts` binds an externally provisioned machine identity to the existing canonical PostgreSQL root. It returns the `SavedWorkerTransactions` callback consumed by `runSavedDraftOnce`. Every callback gets its own canonical transaction, actual session installation, rotation/actor/tenant verification, worker-principal check, build pin and local statement/lock/idle timeouts. Application holds survive rollback; failed commits remain infrastructure failures and cannot become success.

The host snapshots its case and identity. It has no customer HTTP route, session-minting privilege, publication operation or global case enumerator. Use only the supplied `context.client` inside an operation: a query through another connection is outside that transaction and session. The caller owns closing the connection factory after all work and heartbeat activity have drained.

This root remains limited to disposable development targets. The canonical driver and root now share recognition of dated `tivdoc_release_replay_YYYYMMDD` databases as well as historical `tivdoc_v09_*` names. Remote targets still require the exact host, port and database declaration. `postgres`, production names, undeclared hosts and appended replay-name suffixes are refused. A deployment-ready production target policy and worker entrypoint are not supplied by this change.

Use `NodePostgresConnectionFactory` with the real worker connection string, an exact DEV target and a TLS-verifying pool. The isolated proof uses the existing pinned Supabase root CA. Never disable certificate verification or put connection strings/SID/JTI in logs, source control, browser state or evidence. Machine sessions must already exist with the correct tenant, subject and rotation. Revocation is enforced on the next transaction, including a heartbeat or replay.

Failed BEGIN, COMMIT or ROLLBACK marks the pooled connection for destruction on release. This follows node-postgres's documented [`release(true)` behavior](https://node-postgres.com/apis/pool#releasing-clients); a connection with uncertain transaction state must not serve another session. Three isolated regression tests first failed because release returned those connections to the pool, then passed after the change.

The opt-in proof is `src/server/product/processing/saved-extraction-worker.postgres.test.ts` with `TIVDOC_SAVED_EXTRACTION_DB_PROOF=1`, `TIVDOC_SAVED_HOST_DB_PROOF=1`, the private DEV env-file path and private Storage credential-file path. This mode includes the existing saved-job/Storage scenarios and routes the independently provisioned second case through the actual pooled canonical host. Provider transport is deterministic and injected; it is not an OpenAI or accuracy test. Product case/document rows are removed before their exact owned Storage paths; synthetic canonical audit/report history remains explicitly retained.

The first host proof exposed a cleanup bug: revocation worked, and subsequent cleanup incorrectly attempted to use the revoked session. Its two cases, one request identity and two hash-verified Storage files were recovered and removed using the fixture owner's existing authority. The failure and bounded recovery are preserved in `release-evidence/P05-worker-host-cleanup-first-failed.json`. Cleanup now cancels only owned case/tenant jobs through the fixture owner, never reinstates revoked sessions, and records evidence before and after cleanup. The final live result belongs in `release-evidence/P05-saved-worker-host-db.json` and must be read independently of unit-test results.

Still required: executable host packaging, managed session lifecycle, scheduled invocations and unknown-provider-outcome reconciliation; live provider credentials/calibration; reviewed monetary/evidence binding and customer projection/publication. This host is not a deployed daemon, a production activation or completion of P05/P00–P13.
