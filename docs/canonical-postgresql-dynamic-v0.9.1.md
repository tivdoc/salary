# Canonical PostgreSQL dynamic verification V0.9.1

Run the hermetic proof from the repository root with:

```text
npm run verify:postgres:dynamic
```

This V0.9.1 verification command is pinned to Node.js `22.22.2`; its JavaScript launcher fails closed before loading the TypeScript runtime on any other Node version. The exact runtime version is recorded and independently verified in the environment receipt. This harness prerequisite does not change the broader product runtime statement in the repository README.

The command fails closed unless it is on `codex/tivdoc-engine-foundation`, descends from the required V0.9 base, and has a clean tracked and untracked source worktree. Source identity uses the fixed Git for Windows 2.52.0 binaries with pinned hashes and a sanitized environment; replacement refs, grafts, alternates, hidden index flags, redirected Git directories, and nonphysical repository roots are rejected. It scans source text for high-confidence secret material, rejects tracked customer artifacts, requires `supabase/.temp/` to remain absent, and validates the preserved V0.9 static receipt, manifest, ZIP, independent verifier, exact base HEAD/tree, ordered 24-item ledger and PC-22 blocker. Initial and postflight static-package hashes must match. The complete matrix requires the harness-owned local server because ownership authorization and a genuine stop/start boundary are mandatory; an explicit URL without a separately verified ownership marker is rejected before any mutation.

## Isolated PostgreSQL architecture

When no explicit target is present, the harness uses the PostgreSQL 17.11 Windows binary archive published by EnterpriseDB and linked for advanced users by PostgreSQL.org. It downloads the exact 340,722,468-byte archive when absent, over HTTPS from the pinned official URL, rejects redirects and size/hash drift, validates the pinned archive SHA-256, rejects path escapes and link entries, and performs a fresh user-space extraction. Before any PostgreSQL executable runs, it rejects reparse points/hardlinks and verifies the complete 20,383-file, 904,941,738-byte distribution tree plus every required executable hash. A fixed protected Windows PowerShell path performs the bounded .NET ZIP extraction, and an explicit token check rejects elevated execution. The bootstrap also reconciles the installed `node-postgres` runtime and all transitive runtime packages to pinned lockfile integrity values and complete package-tree hashes before loading them. It creates a user-space cluster under `.tmp/postgresql-dynamic-v0.9.1/`, listens only on `127.0.0.1` at a random high port, uses SCRAM credentials, UTF-8, UTC and data checksums, and never installs a service or changes system configuration. Binaries remain under `.tools/postgresql/`; clusters, logs and backups remain under `.tmp/`; all are Git-ignored.

The test-only compatibility bootstrap creates only the Supabase-style roles and storage objects required by the repository migration chain. It is not a Supabase emulator. A successful run proves `REAL_POSTGRESQL_DYNAMIC_PROOF`; it does not close `ISOLATED_SUPABASE_MIGRATION_RLS_VERIFICATION_REQUIRED`.

## Matrix

The runner applies the exact ordered migration chain to a clean database, reconciles the pinned canonical tables, indexes, functions, triggers, policies and constraints, verifies the fixed SHA-256 of every migration, upgrades a seeded pre-canonical database, dynamically verifies the intended metadata backfill plus terminal immutability, and proves controlled transactional migration failure and recovery. PostgreSQL 17 exposed one genuine `42710` portability defect in the historical foundation SQL: an explicit check-constraint identifier collided with the name PostgreSQL generated for an inline check in the same table. V0.9.1 contains one pinned, receipt-backed identifier-only amendment; the baseline and amended hashes, error code, exact rename and `sql_semantics_changed: false` are recorded in evidence. No other historical bytes are relabelled. A real `node-postgres` pool then instantiates `canonical-postgres-application.ts` and exercises all 14 canonical bindings with inert synthetic fixtures.

It next proves persistence across a clean PostgreSQL stop/start and a fresh Node process, including adapter-level idempotency, audit, job, outbox, approval and no-duplicate-effect replay; tests real `anon`, `authenticated`, `service_role`, and non-bypass tenant-policy sessions, including own-tenant visibility, cross-tenant read isolation, a real cross-tenant write rejection on every one of the 27 policy tables, and security-definer ACLs; injects application-hook failures across TX-01 through TX-08; and runs deterministic multi-connection duplicate, fencing, approval, stale-revision, idempotency, outbox, conflicting-update, and retry races with exact accepted/rejected counts, expected domain codes and durable observations. The RLS denominator uses two clearly labelled synthetic, non-legal finding controls and two synthetic immutable job-history controls so all 27 policy tables have positive rows in both tenants; the finding controls are deleted immediately after the probe. No customer document, live provider, real finding, or active legal source/rule/parameter is used.

Finally, official `pg_dump` and `pg_restore` create a custom-format backup in the ignored runtime directory, restore into a fresh isolated database, compare table counts and record-set/schema hashes, reconstruct the real application root, replay durable state, and rerun RLS checks. Raw backups and database pages never enter evidence.

## Evidence and limits

Safe receipts are written to `output/canonical-postgresql-dynamic-v0.9.1/final/`. The package contains environment, full migration hashes and the portability-amendment receipt, a recomputable lower-bound breakdown of observed application-driver acquisitions, 14-capability, restart, RLS, atomicity, concurrency, backup/restore, verified shutdown, preflight, Git, regression and acceptance receipts. It excludes credentials, connection strings, row contents, customer data, logs and dumps. PostgreSQL is stopped and independently confirmed stopped before PASS evidence is minted. The deterministic ZIP is built twice, compared by SHA-256, extracted entry-by-entry, matched byte-for-byte to the manifest, independently rebuilt, and semantically verified against the underlying receipts. The excluded independent-verifier output is itself path/size/hash-bound by the outer wrapper receipt.

The command runs focused V0.9/V0.9.1 tests, the full test suite, ESLint, TypeScript without emit, a Next.js production build, and the existing V0.9 acceptance command before issuing a dynamic `24/24` receipt. This proof is local and isolated; it does not authorize deployment, remote migrations, Production or Shadow Mode, and it does not claim Supabase-platform verification or Production readiness.
